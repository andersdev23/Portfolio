Git: commits pequenos, histórico que faz sentido

O histórico de um projeto também é uma forma de comunicação. Um commit que responde a uma mudança clara ajuda a revisar o trabalho e a entender por que uma decisão foi tomada.

Defina a intenção antes de agrupar arquivos

“Pequeno” não significa uma quantidade fixa de linhas. Um commit útil reúne uma alteração coerente: corrigir uma validação, adicionar uma página de artigo ou ajustar o menu no celular. A ideia é conseguir explicar o resultado em uma frase.

Misturar uma correção de comportamento, uma troca de formatação e uma funcionalidade nova torna a revisão mais cansativa. Se os assuntos podem ser entendidos e validados separadamente, vale separá-los no histórico também.

Antes de começar, observe o estado do repositório. Assim você distingue o que já estava em andamento daquilo que vai mudar agora.

Terminal
git status --short
git diff

Dê um contexto ao trabalho com uma branch

Uma branch permite desenvolver uma linha de trabalho com um nome reconhecível. O comando abaixo cria uma branch e passa a trabalhar nela. O nome é um exemplo: use algo que descreva o objetivo da alteração.

Terminal
git switch -c feat/paginas-artigos

Criar a branch não publica o projeto nem abre um pull request. É uma organização local do trabalho. Alterações que ainda não foram registradas não se tornam um backup só porque você mudou de branch; continue inspecionando e registrando o que estiver pronto.

Escolha o que vai entrar e revise novamente

O próximo exemplo supõe que blog.html e artigos/novo-artigo.html sejam os arquivos alterados para uma publicação. Adicionar caminhos explícitos ajuda a perceber se algum arquivo entrou por engano.

Terminal
git add blog.html artigos/novo-artigo.html
git diff --staged
git status --short

O conteúdo preparado fica na área de staging. A revisão de git diff --staged mostra o que está pronto para o próximo commit. Se você editar o arquivo depois de executar git add, a nova edição precisa ser preparada novamente para fazer parte desse mesmo registro.

Quando a mudança estiver revisada e validada, escreva uma mensagem que descreva o resultado.

Terminal
git commit -m "Adiciona página de artigo e link no blog"

Retire um arquivo da seleção sem apagar a edição

Se um arquivo entrou na área de staging antes da hora, você pode retirar essa seleção com o comando abaixo. Neste uso, --staged atua sobre o índice; as edições no arquivo de trabalho permanecem.

Terminal
git restore --staged blog.html

Confira o resultado com git status e continue a revisão. Entender a diferença entre o arquivo de trabalho, a área de staging e o histórico evita tratar todos os comandos de restauração como se fizessem a mesma coisa.

Escreva para quem vai revisar depois

Uma mensagem como “ajustes” não conta o que mudou. “Corrige navegação dos artigos no blog” permite antecipar o objetivo antes mesmo de abrir o diff. Quando houver uma decisão menos óbvia, o corpo da mensagem pode explicar o motivo.

Antes de registrar, confira se o projeto continua funcionando e se não foram incluídos arquivos temporários. Esse cuidado não precisa transformar cada mudança em um processo longo: basta uma revisão proporcional ao que foi alterado.

O resultado é um histórico que ajuda na manutenção. Cada commit se torna uma etapa compreensível, em vez de um conjunto de arquivos sem relação aparente.
